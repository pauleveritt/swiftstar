# GLM 5.3 review of the P11 dispatch-driver recommendation

**Status:** research note; external review captured as written, with the
accepted/rejected synthesis. Not a plan.
**Date:** 2026-08-23
**Reviewer:** OpenRouter `z-ai/glm-5.3` (temperature 0.2).

Context: during P11 brainstorming, the question "how is a dispatch driven" was
presented as three options — (A) the orchestrating model dispatches via a
`dispatch` tool; (B) the plan/app dispatches deterministically; (C) both,
staged (B first, A later). The recommendation under review was C-with-B-first.
The review's findings F1–F3 and changes R1–R6 were accepted; one refinement
(the dispatch event is a host-tool riding P9's `tool_request`/`tool_result`,
not a new wire kind) collapses most of F1.1/F1.2 and was itself invited by the
review. The accepted findings are folded into the spec as D4, D10, D11.

## Prompt sent

You are reviewing a design recommendation for a local-LLM macOS app (SwiftStar).
Be adversarial and technically rigorous: find the hidden flaw, challenge the
reasoning, do not agree to be agreeable. Your review will be read and either
accepted or rebutted point-by-point.

## Context (settled, verified facts — do not re-litigate)

Phase P11 "Subagent pool": context-isolated subagents sharing ONE locked engine,
ending at the phase's own measurement gate. Prior phase P10 shipped isolated
dispatch: a typed HandoffPacket (taskText, exact writableFiles, validationCommand,
per-file baselines, turn/tool budgets) runs in a disposable git worktree and
returns a candidate ref (commit) or a typed receipt. The worker gets
read/write/edit and no bash; every mutation is revision-checked against
writableFiles.

Hard constraints discovered by source verification:
1. The model line is serialized: its family is excluded from the engine's
   cross-session batch path unconditionally. The pool is a QUEUE over one
   serialized engine, not a scheduler over concurrent sessions.
2. The win is the CONTEXT CURVE, not parallelism: eight 16k-token prefills run
   sequentially cost ~4.2x less than one 131k prefill (an upper bound). The
   measurement gate must measure the real gap under that ceiling and must NOT
   expect a parallel-throughput win.
3. Sessions are expensive: ~6.1 GB GPU scratch each plus KV (49,152 * ctx +
   75,497,472 bytes). Levers are small-ctx workers and snapshot/rewind of idle
   tiers.
4. The engine already has every session primitive (session_new, rewind,
   save_payload/load_snapshot, common_prefix, eval) but the agent program is
   SINGLE-worker; BRIEF names a future engine patch "--subagent-pool with worker
   ids" (fork divergence #11).

## The decision under review

How is a dispatch DRIVEN? Three options:

A. The orchestrating model dispatches: the root agent session is given a
   "dispatch" tool whose argument is a handoff packet; the model decides what to
   delegate. Routing logic (parallelism proofs, thinking-requirement test,
   executor choice) lives in the model, the app proves/enforces declared intent.
   Requires a new tool + engine dispatch event.

B. The plan/app dispatches deterministically: the handoff-packet maker is the
   plan author or the app (P10's model generalized to N queued packets). The
   orchestrator model never sees the pool. No new tool, no engine dispatch event,
   but no model-driven delegation.

C. Both, staged: P11 first delivers B (the pool + queue over app-provided
   packets, fully testable against a fake engine with no model judgment), then
   adds A (dispatch tool + routing proofs) as the model-facing surface once the
   pool exists. If the measurement gate ends the phase, B is the phase's spine
   and A may slip to a later phase.

## The recommendation being reviewed

Recommend C, with B first. Reasoning:
- B is the honest measurement-gate substrate: deterministic workers, no model
  judgment to confound the context-curve number.
- A is where the "dispatch decision" (routing axes) backlog actually lives, but
  it needs the pool to exist first to be more than a spec.
- The whole phase already sequences: (1) worker-id wire contract + fake engine +
  Swift pool against the fake, (2) real --subagent-pool C patch behind it,
  (3) measurement gate.

## Questions

1. Is staged C correct here, or is there a hidden flaw in deferring model-driven
   dispatch (A) out of P11?
2. If you would change the boundary between B and A, or the sequencing of the
   three parts (wire contract -> C patch -> measurement), say exactly how.
3. Name the single highest-risk assumption in C and how you would de-risk it.

## Response (verbatim)

## Verdict

C's ordering is right and I won't fight it: B before A, fake engine before real patch, contract before both. What I reject is C's **exit criteria** and its **claim about what the gate measures**. The recommendation contains an internal contradiction (it sequences contract-first, then stops the contract one surface short of A) and a measurement error (it calls the treatment a confound). Accept the skeleton; reject the gate semantics and the slippage clause.

## Q1: The hidden flaw in deferring A

**F1 — A is not one thing, and C defers both halves of it.** Split it:

- **A-plumbing**: dispatch tool schema, engine dispatch event, receipt return into the orchestrator context, orchestrator session suspend/resume around worker runs.
- **A-routing**: parallelism proofs, thinking-requirement test, executor choice.

Only A-routing "needs the pool to exist to be more than a spec." A-plumbing doesn't need a working pool — it needs the **wire contract and the engine patch, both of which are P11 artifacts frozen at the gate**. Deferring A-plumbing past the gate means:

1. The worker-id contract (part 1) omits dispatch-event and receipt-correlation types, so the contract churns when A lands — violating the recommendation's *own* contract-first logic.
2. `--subagent-pool` (fork divergence #11) gets reopened for a second engine round. The gate then certified patch v1; you ship v2 with different session-interleaving behavior. Nobody re-runs gates for "small" patches. The certificate decays silently.
3. The single riskiest engine path in the design — a **live session suspended via save_payload, worker run, session restored** — is exactly the path B never exercises. Under B the orchestrator isn't a session at all; the app drains packets, and snapshot/rewind is only tested on idle workers. A's dispatch loop is the first time this interleave runs, and C defers it untested past the gate.

**F2 — "no model judgment to confound the number" mistakes the treatment for a confound.** The win is a function of the packet distribution: taskText size, cross-packet context overlap, failure/retry rate, receipt volume fed back to the orchestrator. Under B those are constants chosen by a plan author who can write perfectly-sized packets. The gate samples the curve at its most favorable point and calls the result "the real gap." That's not removing a confound; that's conditioning on the best case. The gate is internally valid and externally invalid: it can go green while saying nothing about whether model-driven dispatch — the actual product bet, per the BRIEF's routing-axes backlog — achieves any win. And that green gate is then the justification for keeping the fork. A mechanics measurement is feeding a value decision.

Note also that the invariants making B safe are currently human-guaranteed: disjoint `writableFiles` and fresh per-file baselines come from the plan author. Under A the *model* must produce them and the app must prove them. That's A-routing being load-bearing for correctness, not just efficiency — another way the gate's inputs are dispatcher-dependent.

**F3 — "A may slip" has no forcing function.** B standalone is a queue with no producer. If A slips to P12 and P12 has its own scope, you're paying fork maintenance on a patch whose only consumer is a test harness. Phases that end with "the interesting part slipped" are how infrastructure rots.

So: staged C, correct. Deferring A-routing, correct. **Deferring A-plumbing is the hidden flaw.**

## Q2: Exact boundary and sequencing changes

**R1.** Move the boundary inside A: A-plumbing becomes P11 exit criteria (non-slippable); A-routing stays post-P11 (slippable, fine). What may slip is the intelligence, not the interface.

**R2.** Part (1) amended: the wire contract reserves dispatch-event and receipt types (tool-call surface, worker-id correlation, receipt schema) now, and the fake engine implements them. Marginal cost is near zero — the fake is being written anyway — and it removes the contract churn in F1.1.

**R3.** Part (2) amended: the engine patch ships dispatch-event emission behind a flag, and the orchestrator suspend/resume path is implemented and contract-tested even with nothing user-facing consuming it. One fork round, not two; the gated artifact is the artifact A builds on.

**R4.** Part (3) amended — the gate reports three things, not one number:
- **(a) Overhead ratio**: realized win / analytic 4.2× ceiling on canonical packets. This is what B honestly measures; label it as such.
- **(b) Sensitivity envelope**: deterministic perturbations of the canonical packets — taskText bloat (×1.5, ×2), failure injection at fixed rates under a fixed retry policy, packet-count sweeps. Still zero model judgment; determinism preserved. Output: win as a function of packet quality, and the threshold at which the win stops justifying the fork.
- **(c) Instrumentation**: count tokens *actually evaluated*, not tokens nominally in packets — the gap between them is exactly where snapshot/restore re-eval bugs hide. Also peak resident memory and snapshot save/restore counts. Under A the orchestrator's residency competes with worker scratch; if every dispatch round-trip evicts and restores orchestrator KV, the per-receipt restore cost is a term B's gate is structurally blind to.

**R5.** Sequencing: an A-plumbing vertical slice (model emits one dispatch against the *fake* engine, queue runs, receipt returns into the orchestrator context) runs concurrently with part (2) — it depends only on the fake from part (1). Existence-gated, not quality-gated.

**R6.** Governance: add a use-it-or-lose-it clause. If A-routing hasn't landed within a bounded window after P11, the engine patch gets flag-gated off or reverted. Divergence #11 should not be a permanent tax on an unconsumed feature.

Minor: fake-first is right, but derive the fake's session semantics (rewind, save/load, common_prefix) from the real engine via a shared contract-test corpus, or the Swift pool gets rebuilt after part (2) anyway.

## Q3: The single highest-risk assumption

**A1: That the context-curve win is dispatcher-invariant — a property of the pool — such that a gate run on deterministic hand-authored packets is decision-relevant for the model-driven product.**

Why this one over the obvious runner-up (contract stability / no-second-fork)? Contract churn is *loud*: you discover it the day A starts and pay rework. A1 fails *silently*: the gate passes, the fork is kept, A slips with a green certificate in hand, and the first evidence that model-authored packets (verbose taskText, overlapping context, retries, receipt integration) erode the win arrives a phase late — after the fork tax and the pool have been carried the whole time. Silent wrong conclusions outrank loud rework.

De-risk, concretely: R4(b) converts the point estimate into an operating envelope *without* giving up the recommender's own virtue — you don't need the model to sample the packet distribution, you need to know how the win *responds* to the distribution, and deterministic perturbation gives you that. The envelope then yields a packet-quality threshold that becomes A-routing's acceptance criterion, so A's phase verifies against the envelope without re-running the full gate. R5's smoke test covers the one failure — the dispatch loop doesn't close at all — that makes every number before it moot.

## What I'd accept vs. rebut

I'd accept a rebuttal that shows the dispatch event is app-side, not engine-side (that would collapse F1.2/F1.3 and most of R3 — but the brief says "engine dispatch event," so show me). I'd accept an argument that orchestrator suspend/resume is out of scope because receipts are integrated deterministically by the app via disjoint-worktree merges — but then say so, because that's a product decision that B is a complete feature and A is an enhancement, which contradicts the BRIEF's routing-axes backlog and changes what the gate is for. What I won't accept is the current framing: a gate that measures the ceiling calling itself the real gap, certifying an artifact that A will immediately modify.
## Synthesis (accepted / refined)

- **Accepted F1 (A-plumbing vs A-routing):** "model-driven dispatch" splits into
  plumbing (dispatch tool schema, receipt correlation, orchestrator
  suspend/resume) and routing (parallelism proofs, thinking-requirement test,
  executor choice). Only routing "needs the pool." Plumbing is non-slippable P11
  scope; routing stays deferred. → spec D10.
- **Accepted F2 (treatment vs confound):** the win is a function of the packet
  distribution; a gate on hand-authored packets samples the curve at its most
  favorable point and is externally invalid. → the gate is an envelope, spec D11.
- **Accepted F3 (slippage forcing function):** a "may slip" clause with no
  forcing function rots the fork. → use-it-or-lose-it governance, spec D11.
- **Accepted R1–R6** (boundary inside A; reserve contract types now; contract-test
  suspend/resume; three-part gate; fake-first with shared contract corpus;
  governance).
- **Refinement (invited by the review's own "I'd accept a rebuttal…"):** the
  dispatch event is app-side — a host-tool on P9's existing
  `tool_request`/`tool_result`, so it needs no new wire kind and no second fork
  round for emission. What remains genuinely new engine surface is the pool
  itself (N sessions, one engine, worker ids, session interleave). → spec D3/D4.
