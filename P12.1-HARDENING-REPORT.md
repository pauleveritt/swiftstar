## Judgment call: where does the "packet version" check belong?

The brief flagged this as genuinely ambiguous and asked me to investigate
rather than assume. I did, and concluded the check belongs in
**`PacketFrontmatter.parse`/`requireKnownPacketVersion` (the parser layer)**,
not in `HandoffPacketValidator.validate(_:)`. Reasoning:

- `HandoffPacket` (the type `HandoffPacketValidator.validate(_:)` operates
  on) has no version field of any kind — nothing to check post-construction.
- The schema doc explicitly frames "packet version" (rule 1) the same way it
  frames "role enum" (rule 2), which it says outright is "enforced at parse,
  not validate." Rule 1 and rule 2 are adjacent and structurally identical
  (a scalar that must be one of a small known set, checked once at parse
  time) — the doc's own precedent points at the parser.
- The doc separately says `packet:` is "currently parsed and discarded" —
  i.e. it already exists as parsed data (`fields.scalars["packet"]`) inside
  `PacketFrontmatter`, just unused. The natural fix is to stop discarding it
  where it's already sitting, not to smuggle a new field onto `HandoffPacket`
  just so a different file can check it.
- By the time a `HandoffPacket` exists in memory (whether from the parser or
  constructed directly by test/production code, as most of
  `HandoffPacketValidatorTests` already does), the schema version question is
  moot — the caller already committed to a schema when it built the value.

I implemented it as `PacketFrontmatter.requireKnownPacketVersion(_:)`,
called from `parse(_:)` right after `parseFields`, throwing
`PacketFrontmatterError.malformed` for both an absent `packet:` key and an
unrecognized/non-numeric version. This means a packet built directly as a
`HandoffPacket` (bypassing the frontmatter parser) has no version check —
which is consistent with the type having no version field to check, and with
every existing `HandoffPacketValidatorTests` case that constructs a
`HandoffPacket` directly and expects it to validate.

## Concerns / things worth a second look

- **The branch/location mismatch above is the main open item.** I did not
  attempt to reconcile it myself (e.g. by trying to force a checkout of the
  named branch into this worktree, which would have required destructive git
  operations on a shared branch pointer) — flagging it for a human instead.
- **Block scalar support is intentionally narrow.** I implemented only the
  literal `|` style (plus its `|-`/`|+` chomping variants, though chomping
  itself isn't differentiated — all three currently clip trailing blank
  lines the same way) since that's what the bug report and schema doc
  reference (`command: |`). Folded (`>`) style is not supported and a
  `>` value would just be treated as an ordinary scalar (`">"` literal) —
  same class of bug, but out of scope per the brief and not something the
  schema doc's examples ever use.
- **`stripTrailingComment` is a simple quote-tracking scanner**, not a full
  YAML tokenizer. It correctly handles the cases in the tests (comment
  outside quotes, `#` inside a quoted fragment) but a pathological
  hand-crafted value with unbalanced quotes could confuse it. Given this
  parser already documents itself as "a closed set of scalars ... rather
  than pulling in a general YAML dependency," I judged this proportionate
  rather than under-built.
- I did not touch `DispatchPacketBuilder` or the agenttest harness wiring —
  out of scope per the brief, which was specifically about
  `HandoffPacketValidator.swift` and `PacketFrontmatter.swift`.
